# 상세페이지 추가 수집 계획 — 검토안

- 작성일: 2026-11-13
- 현재 단계: 수집 컬럼·계획 검토. 이 문서 작성으로 실행 승인을 대신하지 않는다.
- 진행 순서: **컬럼 확정 → 계획 승인 → 실행 승인 후 구현·수집**.

## 1. 수집 대상

기존 목록 완본 `yes24_it_mobile_list.csv`의 상품 ID를 사용한다. 목록 전체를 다시 탐색하지 않고, AI 키워드 일치 여부와 관계없이 대상 기간의 IT·모바일 상품을 상세 수집한다.

| 구분 | 상품 수 | 처리안 |
|---|---:|---|
| 기존 목록 전체 | 46,081 | 원본 유지 |
| 2010년 이전 | 18,212 | 이번 상세 수집에서 제외 |
| 발행월 누락 | 30 | 대상 선정 보류 |
| 2010년 이후 전체 | 27,839 | 이 중 미래 발행월 처리 필요 |
| 2026년 12월 이후 | 15 | 기존 보고서와 맞춰 이번에는 제외 제안 |
| **제안 대상: 2010-01~2026-11** | **27,824** | 발행월 기준으로 대상 ID 고정 |

2010년은 이번 분석의 범위로 설정한 기준이며, 그 이전에 AI 관련 도서가 없었다는 의미는 아니다. 2026년 11월 표시 상품에는 수집일 이후 출간 예정이 포함될 수 있으므로 상세 발행일로 구별한다. 상세 발행일이 목록의 발행월과 다르면 덮어쓰지 않고 대조 대상으로 남긴다.

기존 상세 CSV 1,010건 중 제안 대상에 해당하는 상품은 897건이다. 이 중 소개와 목차가 모두 채워진 상품은 872건이다. 기존 자료는 한글 분류 경로를 가지고 있지만 경로별 분류 코드는 저장하지 않았으므로, 새 명세를 충족하는지 확인하기 전에는 수집 완료로 세지 않는다. 코드·한글명 대조로 보완할 수 있는 자료는 재사용하고, 추가 요청은 미수집·보완 필요 상품에 한정한다.

## 2. 수집 컬럼안: 10개

| 컬럼 | 내용·형태 | 분석·관리 목적 |
|---|---|---|
| `product_id` | 문자열 상품 ID | 목록본 연결·중복 요청 방지 |
| `product_url` | 상세페이지 주소 | 원문 확인 |
| `title` | 상세페이지 제목 | 제목 키워드 분석·목록본 대조 |
| `subtitle` | 부제, 없으면 빈값 | 제목에서 빠진 주제 보완 |
| `publication_date` | 확인된 발행일 `YYYY-MM-DD`, 일자 확인 불가 시 빈값 | 시기별 분석·출간 예정 구별 |
| `publication_date_raw` | 화면에 표시된 발행일 원문 | 날짜 정규화 검증·연월만 있는 자료 보존 |
| `isbn13` | 문자열 ISBN13, 없으면 빈값 | 판본·중복 후보 대조. ISBN만으로 같은 저작물이라고 확정하지 않음 |
| `categories` | 코드·한글명·전체 경로를 담은 JSON 배열 | 하위 분야별 비교·복수 분류 보존 |
| `description` | 책 소개 텍스트, 줄바꿈 유지 | 제목에 없는 주제 확인·분류 보완 |
| `table_of_contents` | 목차 텍스트, 줄바꿈 유지 | 다루는 기술·활용 내용 확인 |

가격·출판사·평점·판매지수·리뷰·무게·크기·표지는 이번 수집안에서 제외한다. 기존 목록의 발행월·분류 출처 등은 상품 ID로 연결해 사용한다.

`categories`의 구조 예시이며 아래 값은 실제 분류를 확정한 것이 아니다.

```json
[
  {
    "code": "최하위 분류 코드",
    "name": "최하위 분류 한글명",
    "path": ["국내도서", "IT 모바일", "상위 분류명", "최하위 분류명"]
  }
]
```

상세페이지의 분류 링크에서 코드와 실제 한글명을 함께 읽는다. 상품에 붙은 모든 분류 경로를 보존하고, 수상·미디어 추천 분류는 도서 분류와 섞지 않는다. 경로별 연결 관계를 유지해 서로 다른 분류의 코드와 이름이 잘못 짝지어지지 않게 한다.

추출한 각 단계의 코드는 한글명·상위 코드·경로와 함께 별도 분류 사전에 누적한다. 기존 목록의 `source_category`도 이 사전으로 한글명을 연결한다. 제안 대상의 출처 코드는 14종이며, 상세 링크로 확인되지 않는 코드는 필요한 분류 페이지만 추가 확인한다. 이름을 코드에서 추측해 채우지 않는다.

## 3. 건별 대기와 묶음별 휴식

| 항목 | 제안 설정 |
|---|---|
| 동시 실행 | 한 PC에서 프로세스 1개·동시 요청 1개·HTTP 세션 1개 |
| 작업 순서 | 대상 ID를 한 번 섞어 저장하고 같은 순서로 재개 |
| 건별 대기 | 응답이 끝난 뒤 다음 요청까지 매번 무작위 5~20초 |
| 묶음 크기 | 묶음마다 무작위 정수 100~150회 요청 |
| 묶음별 휴식 | 묶음 종료 후 무작위 5~10분 추가 대기 |
| 대기 적용 범위 | 상세·분류 확인·일반 오류 재시도 등 모든 HTTP 요청에 공통 적용 |

건별 대기와 묶음별 휴식은 합산한다. 실패·재시도 요청도 묶음 요청 수에 포함한다. 묶음은 동시에 실행하는 세션이 아니라, 같은 수집기가 순서대로 처리하는 작업 단위다.

예: 120회 순차 요청(매회 응답 뒤 5~20초 대기) → 7분 추가 휴식 → 다음 143회 요청 → 9분 추가 휴식. 마지막 작업 뒤에는 불필요한 휴식을 두지 않는다.

사이트의 공개 접근 정책과 서버가 지정한 대기시간을 우선한다. 접근 제한이나 반복 리다이렉트가 감지되면 저장 후 중단하며, 세션을 바꿔 계속 요청하지 않는다. 무작위 대기는 요청 집중을 줄이는 방식으로 사용한다.

## 4. 저장·오류·재개

- 기존 목록·상세 CSV와 그 상태 파일은 원본으로 보존하고, 새 명세의 상세 자료는 별도 UTF-8 파일로 저장한다. JSON·줄바꿈·쉼표가 CSV 안에서도 보존되도록 처리한다.
- 완료 ID와 결과를 매건 저장한다. 현재 묶음의 남은 요청 수·휴식 종료 시각도 보존해 재시작이 예정된 휴식을 건너뛰지 않게 한다. 중복 실행은 잠금으로 막는다.
- 수집시각·시도 횟수·응답 코드·완료/실패 상태·필드별 결측 사유는 별도 관리 파일에 기록한다. 분석용 10개 컬럼과 구분한다.
- 소개·목차의 빈값은 원문 미등록과 추출 실패를 구별한다. 원문 부재를 확인할 수 없으면 확인 필요로 남기고, 빈값을 자동으로 성공이나 비AI로 판정하지 않는다.
- 통신 오류·일시적 서버 오류는 건별 대기를 지키면서 최대 2회 추가 시도하고 대기시간을 늘린다. 사이트의 제한 응답이나 제한 페이지로의 이동은 자동 재시도를 멈춘다. 상품 삭제·접근 불가는 별도 사유로 남긴다.
- 중단된 결과는 전체 완료 자료로 취급하지 않는다. 완료·실패·보류 수와 발행연도별 수집률을 함께 확인한다.

## 5. 승인 후 실행 순서와 예상 시간

1. 승인된 컬럼·대상 범위·대기 설정을 고정하고, 기존 목록에서 수집 대상 명단을 만든다.
2. 기존 상세자료와 분류 경로를 대조해 재사용·보완·신규 요청 대상을 나눈다. 기존 수집기의 고정 간격·상세 모드는 그대로 실행하지 않고, 날짜 필터·두 단계 무작위 대기·단일 실행·새 명세를 검증한다.
3. 실행 승인 범위 안에서 서로 다른 연도·복수 분류·소개/목차 결측을 포함한 소량 10건을 확인한다. 컬럼 추출과 대기·저장이 정상일 때 전체 대상에 이어서 적용하고, 구조 불일치·접근 제한 시 중단한다.
4. 완료 후 대상 ID 대조, 중복 ID, 날짜, 코드–한글명, JSON/텍스트 손상, 결측 사유와 연도별 수집률을 검증한다.

재사용 없이 27,824건을 모두 요청한다고 가정하면 평균 묶음 크기는 125회, 묶음은 약 223개다. 건별 평균 대기 12.5초와 묶음별 평균 휴식 7.5분을 합하면 **대기시간만 약 124시간(연속 실행 약 5.2일)**이다. 통신·분류 확인·오류 처리·PC 중단 시간은 별도로 더해지며, 실제 요청 수와 완료 시점은 재사용 점검 및 실행 상황에 따라 달라진다.

## 6. 이번 검토에서 결정할 것

1. 위 10개 컬럼으로 확정할지, 추가·제외할 컬럼이 있는지.
2. 2010년 이후 중 기존 보고서와 같은 **2010-01~2026-11의 27,824건**을 대상으로 할지. 2026년 12월 이후 예정 상품 15건을 포함하면 27,839건이다.
3. 건별 5~20초·묶음 100~150회·묶음 휴식 5~10분 설정을 사용할지.

컬럼과 계획이 승인되어도 **실제 수집 시작은 별도 실행 승인 후** 진행한다.

## 작업 정의와 검증

- Goal / Reason: 대상 건수를 확인하고, 상세 컬럼과 두 단계 무작위 대기 수집 계획을 검토 가능한 문서로 만든다.
- Scope: 이 계획 문서만 작성한다. 수집기 수정·네트워크 요청·데이터 변경·수집 실행은 포함하지 않는다.
- Acceptance Criteria: 대상 건수·재사용 후보 수를 실제 CSV로 확인하고, 컬럼 의미·한글 분류 수집·요청 간격·중단/재개·소요 시간·승인 단계를 명시한다.
- Tests: 로컬 CSV 전체 파싱과 상품 ID 교집합, 기간별 건수·소개/목차 채움 여부, 예상 시간 산술 및 diff를 확인한다. 문서 작업으로 코드 테스트는 해당하지 않는다.
- Dependencies: 기존 목록 완본·상세 부분 자료·수집기와 교수님이 제안한 건별/묶음별 대기 방식.
- 검증: 목록 46,081건을 기간·결측으로 분할했고, 제안 대상 27,824건 및 기존 상세와의 교집합 897건(소개·목차 모두 있음 872건)을 대조했다. 이 단계에서 HTTP 요청과 수집 실행은 하지 않았다.
